# 踩過的雷

已經花時間查過、確認過的坑。之後要改相關的地方，先看這裡，不要再撞一次。

## 資料庫連線

- **連線快取一定要用 `globalThis`，不能只在開發模式快取。**
  常見寫法是「只有 dev 才快取，正式環境模組只載入一次」——這是錯的。
  打包之後 RSC 跟 SSR 是不同的 chunk，同一支模組會被載入不只一次，
  每一份都會自己開一組連線池，Supabase 的連線額度很快就被吃光。

- **不要用 postgres.js 的 `connection` 選項去設 `statement_timeout`。**
  那是走 PostgreSQL 的 startup parameter，Supabase 的連線池（pgbouncer）
  會擋掉它不認得的參數，結果是連線根本建不起來。

- **Supabase 要用 Transaction pooler（`:6543`），不要用 Direct connection（`:5432`）。**
  serverless 直連會把連線數吃光。

- **本機連 Supabase 會中途卡死（2026-08-11 查過）。**
  連線是通的（TCP Established），但資料傳到一半就不動，資料庫端顯示查詢卡在
  `Client/ClientRead` 超過兩分鐘。已排除：連線洩漏、資料庫鎖定衝突、查詢太慢、
  資料庫本身、Tailscale（路由表確認流量走 Wi-Fi 沒經過它）。
  剩下的嫌疑在「家裡 Wi-Fi → ISP → AWS 東京」這段。
  要確認的話：用手機開熱點、電腦連上去再跑一次 `node scripts/verify.mjs`。
  部署到 Vercel 之後沒有這個問題（機房到機房是專線）。

### 2026-08-18 追加：黑畫面的真正原因

症狀是「其他頁都好，只有記帳頁第一次好、之後切回去就一直轉」。查下來是四件事疊在一起：

1. **連線會變成殭屍，而且不會自己好。**
   查詢送出去之後回應永遠不回來 —— 不是慢，是真的不回來（實測把重建機制關掉，
   逾時的查詢一支都沒有遲到回來過）。而且整組連線會一起死，連 `/api/health` 都不回，
   同一時間用獨立腳本開全新連線池連同一個資料庫卻完全正常。
   **所以壞的是手上這幾條連線，不是資料庫。**
   對策：`src/lib/queries.ts` 的 `read()` —— 3 秒沒回應就放棄、整組連線丟掉重建、重試一次。
   有這個機制驗收腳本 35/35 通過，關掉只跑得完 3 項。

2. **`fetch_types: false` 一定要開。**
   postgres.js 每開一條新連線都會先跑一支「問資料庫有哪些陣列型別」的查詢，
   這支在 pooler 上會被砍掉，而它是連線的第一支查詢，一死就把後面的真正查詢一起拖下水。
   我們沒有任何陣列欄位，關掉沒有副作用。

3. **連線池 `max` 一定要 ≥ 單一頁面同時發出的查詢數。**
   連線不夠時 postgres.js 不會等，而是把查詢疊到同一條既有連線上（pipelining），
   經過 pgbouncer 之後疊在後面那支有機率永遠不回來。實測抓到過：
   同一條連線上前一支 59ms 回來、後一支等到 statement timeout。

4. **頁面的資料一支一支查，不要 `Promise.all`。**
   同時發四支查詢等於同時開四條新連線，而「一次開多條新連線」正是最容易出事的時候
   （獨立腳本重現過：全新連線池第一輪五支併發會掛一支，第二輪之後連線熱了就完全正常）。
   排隊查在 Vercel 上跟資料庫同機房只差幾毫秒，很划算。

> 順帶一提，這些都不是 Supabase 的問題：直接對 pooler 打五支併發跑十八輪、
> 連線閒置四分鐘後再用，全部 40～50ms 正常。`statement_timeout` 是 2 分鐘，
> 所以看到「查詢跑 300ms 就被 statement timeout 砍掉」時要知道那是**別人留下來的錯誤**，
> 不是你這支查詢真的跑了兩分鐘。

## 測試腳本本身的坑

- **收合區（`<details>`）裡的東西永遠是「不可見」的。**
  `getByText('薪水').first()` 會抓到「篩選」收合區裡那顆「工讀薪水」分類按鈕，
  然後一路等到逾時 —— 畫面其實完全正常。定位要限定範圍，例如
  `page.locator('li').filter({ hasText: '薪水' })`。
  同理，要填「搜尋備註」之前得先把「篩選」點開（`openFilters`）。

- **點分頁連結之後要等網址真的變。**
  那是普通的 `<a>`，點下去到頁面換掉之間有空窗。沒等的話會在「還沒篩選」的清單上
  做檢查，結果看起來像程式壞掉。

- **驗收的期望值不能寫死。**
  「變動支出 950」那種寫法只有在當月完全沒帳時才成立。腳本現在會先讀當月既有的帳
  當基準再往上加。

## PWA / Service Worker

- **Service worker 預先快取 `/offline` 時，那個網址不能被登入檢查擋下來。**
  被擋就會轉址到登入頁，結果快取起來的是登入頁——真的離線時看到的是一張
  登不進去的登入頁，不是「目前離線」的提示。

- **Service worker 不要中途搶走頁面控制權**（`clients.claim()`），
  會造成登入完成後畫面換不過去。改成等下次開啟才生效。

- **iOS 只有 Safari 能「加入主畫面」**，Chrome 不行。

- **`black-translucent` + `viewport-fit=cover` 會讓內容鑽到瀏海／狀態列底下。**
  所有頁面最上緣都要自己墊 `env(safe-area-inset-top)`，底部墊
  `env(safe-area-inset-bottom)` 避開 home indicator。

## 表單 / 登入

- **登入用最原始的表單 POST + 伺服器 303 轉址，不要用 Server Action。**
  Server Action 成功後要靠瀏覽器端路由跳轉，實測會卡在「驗證中…」不動。
  原生表單送出連 JavaScript 沒載入都能登入。登入是進系統的那道門，選穩定不選漂亮。

## Next.js 16

- `middleware` 已改名為 `proxy`（本專案在 `src/proxy.ts`）。
- 動了 API 或慣例前先讀 `node_modules/next/dist/docs/`，這版跟舊版差很多。

## DeepSeek（口語輸入）

2026-08-20 實作 P2 時對著 API 實測出來的，改 `src/lib/deepseek.ts` 前先看這幾條。

- **可用的 model 只有 `deepseek-v4-flash` 與 `deepseek-v4-pro`。**
  沒有 `deepseek-chat`。動這個字串之前先打一次 `GET https://api.deepseek.com/models`，
  不要憑印象寫。

- **v4 是推理模型，`reasoning_content` 會吃掉 `max_tokens`。**
  `max_tokens: 200` 的時候有 187 個被推理吃光，正文 JSON 直接被截斷，
  `finish_reason` 回 `length`。看起來像模型不會輸出 JSON，其實是被砍掉的。

- **`reasoning_effort: 'none'` 是這個功能能不能用的關鍵。**
  記帳這種抽取任務不需要推理，開著要 3～13 秒（最糟一句 12.9 秒還沒答完），
  關掉是 0.8～1.5 秒，答案完全一樣。手機上這是「能用」跟「不會想用」的差別。

- **模型會混用簡體字**（清單寫「工讀薪水」，它回「工读薪水」），
  所以分類是用**編號**讓它挑，不是讓它回名稱。回名稱就會對不回來、全部掉進未分類。

- **一定要有確認步驟。** 早期 prompt 下「買菜大概三百多吧」被解讀成開伙 0 元 ——
  金額整個消失。規格書第 3 節警告的「金額聽錯很致命」是真的會發生。
  prompt 現在明寫「句子裡只要有金額，isCommunal 一律 false」，
  但這種東西不能只靠 prompt，`src/app/actions/parse.ts` 會再驗一次。

- **解析失敗不能連累已經填好的表單。**
  一開始把 `TransactionForm` 的 `key` 綁在每次解析的 id 上，結果解析失敗時 key 也會變、
  表單重新掛載，使用者手動打到一半的金額被清掉。現在只有解析成功才換 key。

## 測試腳本不可以掃到真實資料

2026-08-20 差一點出事：驗收腳本的清理寫了
`delete from transactions where source = 'line'`。當下沒有 LINE 資料所以沒事，
但等 Gino 真的開始用 LINE，跑一次驗收就會把他所有 LINE 記的帳刪光。

同一天還寫了一支臨時腳本用 `delete from transactions where date = 今天`
去製造「今天沒記帳」的狀態。那次刪到的剛好只有自己的殘留測試資料，
但這種寫法本來就是賭運氣 —— 條件裡沒有任何東西能區分「我造的」跟「真的帳」。

規矩：

- **`scripts/verify.mjs` 裡每一句 delete 都必須綁在 `[E2E]` 標記上。**
  絕對不要用 `source`、`date`、`created_at` 這類會掃到真實資料的條件。
- 口語輸入與 LINE 記的帳，**備註是 AI 寫的、不會帶標記**，所以清理要從
  `raw_inputs.text like '[E2E]%'` 反查 `raw_input_id`，不能改用 `source = 'line'`。
- 臨時的探測腳本也一樣。要「製造出某個狀態」的話，自己插一筆帶標記的資料，
  不要去刪現有的。

### 危險的不只是 SQL，還有「叫程式自己去刪」（2026-08-21，這次真的刪到了）

上面那條規矩只管住了腳本裡的 `delete`。但這次出事的不是 SQL ——
是腳本透過 webhook 送了一句「刪掉」給程式，讓程式自己去刪。

LINE 的「刪掉」指令刪的是 `getLastLineTransaction()`，也就是
**「最近 12 小時內最後一筆 source='line' 的帳」**，這個範圍本質上圈不住測試資料。
腳本的流程是：記一筆 `[E2E]` → 改成 88 → 刪掉（刪到自己的，正確）→
**再送一次「刪掉」去驗「沒東西可刪的時候會不會壞掉」**。
第二次送的時候自己的資料已經沒了，指令就往下找到 Gino 早上真的記的那筆晚餐 20 元，
乾淨俐落地刪掉，而且完全合乎程式邏輯。

前一天寫「以後不會再發生」的時候只想到 delete，沒想到這一條。

規矩補上：

- **凡是測試會觸發「程式自己選一個目標來改／刪」的功能，跑之前先確認那個目標是自己的。**
  `verify.mjs` 現在會先查最近一筆 LINE 紀錄的 `raw_input_id` 對不對得回
  `[E2E]` 的原句，對不上就整段跳過。
- **「邊界狀態」的測試要先確認邊界是真的**。「沒東西可刪」只有在帳本裡一筆
  LINE 紀錄都不剩的時候驗才有意義；有真帳在的時候驗它，等於叫系統去刪真帳。
  現在會數一次，有真的紀錄就印「跳過」。
- **寧可少驗一項，也不要碰到真的帳。** 跳過會在輸出裡明講，看得到就不會忘。

## LINE Messaging API

- **驗簽要用原始的 request body 字串**，`await request.text()` 拿到什麼就簽什麼。
  先 `JSON.parse` 再 `JSON.stringify` 回去，空白與鍵的順序都可能變，簽章就對不上。
- 簽章是 HMAC-SHA256 + **base64**（不是 hex），放在 `x-line-signature` 標頭。
- **webhook 不管發生什麼事都要回 200。** 回 4xx/5xx 的話 LINE 會重送，
  重送就是同一句話記兩筆帳。錯誤要用回覆訊息告訴使用者，不要用 HTTP 狀態碼。
- 回覆用 `POST /v2/bot/message/reply` 帶 `replyToken`；主動推播用
  `POST /v2/bot/message/push` 帶 `to`。一次最多 5 則、文字上限 5000 字。
- `LINE_API_BASE` 是給驗收腳本用的（指到本機假伺服器）。**Vercel 上不要設**，
  設了訊息就送不到 LINE。本機留著反而是好事，開發機不會誤發訊息到你的手機。

## Vercel Cron

- **免費（Hobby）方案一天只能排一次**，寫 `*/15 * * * *` 這種會直接讓部署失敗。
- **只保證落在那個小時內**：`0 14 * * *` 實際可能 14:00～14:59 才觸發。
- **排程一律 UTC**，台北時間要自己減 8 小時（台北 22:00 → `0 14 * * *`）。
- **排程不會跟隨轉址。** 所以 `/api/cron/*` 一定要在 `src/proxy.ts` 放行，
  被導去 `/login` 的話那次提醒就是安靜地消失，連錯誤紀錄都不會留。
- 用 `CRON_SECRET` 環境變數保護：設了之後 Vercel 呼叫時會自動帶
  `Authorization: Bearer <值>`，端點自己比對。沒設就一律拒絕，
  因為這支端點會主動發訊息出去。
- 排程失敗 Vercel **不會重試**，但偶爾會重複觸發，所以動作要能重複執行不出事。

## 測試不要綁在「無障礙名稱」上

導覽列從純文字改成「圖示 + 文字」之後，`getByRole('link', { name: /待結清\s*1/ })`
就失效了 —— 徽章的數字在 DOM 裡跑到文字前面，名稱變成「1 待結清」。
程式完全正常，測試卻紅了。

無障礙名稱是「這個元素裡所有文字接起來」，會跟著排版順序變。
**斷言的目標如果是「某個值對不對」，就給那個元素一個 `data-testid`**，
不要拿名稱去比對。名稱只適合用在「使用者要點的那個東西叫什麼」。

## 圖表不裝套件

原本計畫用 Recharts，實際做下去發現需要的只有兩種圖：

- 堆疊柱狀圖 → 一排 div，高度給百分比就好，天生響應式
- 甜甜圈 → SVG 的 `stroke-dasharray` 控制弧長、`stroke-dashoffset` 轉角度，
  不用自己算 path

各二十幾行，而且都是純伺服器渲染、零 JavaScript。Recharts 要 `'use client'`、
會多背上百 KB 進 bundle，對一個在意冷啟動的手機 PWA 划不來。

甜甜圈的配色有個小陷阱：**相鄰順位的顏色色相要拉開**。第一版第 6 色用了
`#7dd3a8`，跟 `--accent` 幾乎同色，排行榜上「房租」跟「交通」看起來像同一類，
對不回圖上是哪一段。

## 圖表要先想好「幾乎沒資料」長什麼樣

Gino 才剛開始用，六個月的趨勢圖有五個月是空的。空月份如果留白，
整張圖看起來像壞掉；改成畫一條細底線，就看得出「那個月真的沒花錢」。
開發時記得先用少量資料看一遍，不要只用塞好塞滿的假資料驗收。

## 連線池重建的三個坑（2026-08-21）

加了月結算頁與圖表之後，驗收從穩定 70/70 掉到 18～75 之間亂跳，
日誌裡一整排 `write CONNECTION_ENDED`，重建次數幾秒內從 10 衝到 15。
查下來是三個問題疊在一起，缺一個都修不好。

### 一、`end({ timeout: 0 })` 會砍到健康的查詢

重建時直接砍舊池子，把「剛好也在跑、但完全正常」的查詢一起砍掉。
那些查詢會重試，重試又要開新連線，而「一次開很多新連線」正是最初那個
pooler bug 的觸發條件 —— 正回饋，越修越糟。

改成 `end({ timeout: 30 })`。健康的查詢不到一秒就跑完，殭屍反正也不會回應，
三十秒後照樣被強制關掉，我們沒有在等它。代價只是最多 `max` 條連線多留半分鐘。

### 二、重建沒有冷卻時間

剛重建完幾秒內又有查詢逾時，那多半是它本來就跑在舊池子上。再重建一次
只是再送一波新連線出去。加了三秒冷卻，這段期間內的失敗直接用現有的新池子重試。

### 三、模組層快取沒有跟著失效 ← **真兇**

`src/db/index.ts` 開頭就寫了「這支模組會被實體化不只一次」（RSC 與 SSR 是不同
的 chunk）。但 `resetDb()` 只清得掉「呼叫它的那一份」的模組層 `cached`。
另一份還握著已經 `end()` 掉的舊池子，之後每一支查詢都立刻收到
`CONNECTION_ENDED`；而且因為 generation 守衛加冷卻時間，它也重建不了 ——
那一份模組就此永久壞掉。

症狀很好認：**同一支查詢連續四次都是 `CONNECTION_ENDED` 然後放棄**，
而不是逾時。逾時是資料庫沒回應，`CONNECTION_ENDED` 是連線被抽掉，
兩者的成因完全不同。

修法是讓 `cached` 記住自己是哪一代的，`connect()` 進來先比對代號：

```ts
let cached: Db | undefined;
let cachedGeneration = -1;

function connect(): Db {
  if (cached && cachedGeneration === dbGeneration()) return cached;
  // …重新取用，並記下 cachedGeneration = dbGeneration()
}
```

修完之後三次連跑都是 76/76，「被重建砍到」的次數是 0。

> 教訓：**只要有「模組層快取 + 全域狀態」這種組合，模組層那份就必須能驗證
> 自己還新不新。** 只清全域的那份，等於留下一份沒人清得到的舊貨。

## 分類清單跨請求快取

`getCategories` 是全系統被打最兇的一支查詢：每一頁要、每次 AI 解析要、
每次寫入驗證也要（`parse()` 會呼叫 `getCategory`）。但分類幾乎不會變。

改用 `unstable_cache` 跨請求快取，寫入端用 `revalidateTag(tag, { expire: 0 })`
立刻失效。這台電腦上「分類清單逾時」的次數因此從一整排降到個位數。

兩個 Next 16 的細節：

- **`revalidateTag(tag)` 的單參數寫法在這版已棄用**，要給第二個參數
  （`'max'` 或 `{ expire: 0 }`）。少給會直接 TypeScript 編譯錯誤。
- **`updateTag` 只認得 `'use cache'` 打的標籤**，配 `unstable_cache` 要用
  `revalidateTag`。而 `'use cache'` 需要在 next.config 打開 `cacheComponents`，
  那會改變整個 app 的渲染語意（靜態外殼 + 串流），不是為了快取一份分類清單
  就該動的東西 —— 之後真的要整體改造時再一起換。

## 收合的東西，Playwright 仍然說它「看得見」

首頁的手動表單是靠外層 grid 把 `grid-template-rows` 從 `1fr` 壓成 `0fr`、
再用 `overflow: hidden` 裁掉來收合的（比 `max-height` 好：不必先猜一個夠大的數字，
展開速度也不會因為內容長短而忽快忽慢）。

但驗收腳本寫 `expect(送出鈕).not.isVisible()` 會失敗。
**Playwright 的可見性看的是元素自己的 bounding box**，被祖先 `overflow` 裁掉不算數 ——
按鈕自己仍然量得到寬高，所以它回報「看得見」。

要問「使用者看不看得到」，就去量**外層那個容器**的高度：

```js
page.locator('#manual-form > div').evaluate((el) => el.getBoundingClientRect().height)
```

另外收合的時候要記得加 `inert`，不然鍵盤 Tab 會跑進看不見的表單裡，
螢幕閱讀器也會把它念出來。React 19 直接支援 `inert={!open}`。

## 首頁多一個地方顯示同一句話，測試就會壞

「今天開伙 1 次」加到招呼底下那一行之後，月結算卡片的
`getByText('開伙 1 次').count() === 1` 就掛了 —— 頁面上現在有兩個。

數字沒錯、功能沒壞，是測試沒指名要看哪裡。凡是 `count() === n` 的檢查，
都要先用 `getByTestId('month-summary')` 之類把範圍縮到那張卡片裡再找。

## 「這個月 vs 上個月」不能拿總額直接比

第一版寫成 `本月總支出 - 上月總支出`，8 月 20 號打開會顯示「比上個月少 12,000」——
不是省了錢，是**這個月還有 11 天沒過**。這種數字比不顯示還糟，它會讓人放鬆。

正確的比法是**同一個時間點對同一個時間點**：這個月到今天為止 vs 上個月到同一天為止。
實作上要注意兩件事：

- **用日期的「日數」比對，不是往回數幾天。** 往回數 30 天在 2 月會跨到上上個月去。
  `derivePulse` 是用 `Number(date.slice(8)) <= daysElapsed` 篩的。
- **要確認撈回來的區間真的蓋到上個月 1 號**，不然加出來的數字會偏低而且看不出來。
  最壞情況是今天 31 號、上個月也有 31 天＝ 62 天，所以 `PULSE_DAYS = 75`。
  蓋不到就回 `null`，整行不顯示 —— 寧可不講，不要講一個錯的。

翻到**過去**的月份時沒有這個問題（兩邊都是完整的月），要切回整月對整月。
月結算頁是照 `isThisMonth` 分兩種比法的。

## 首頁查詢數的紀律

首頁的查詢是**排隊跑的**（不能用 `Promise.all`，原因見 `(app)/page.tsx` 的長註解），
所以每多一支就多一次來回。「今天花多少」「七天小圖」「連續記帳」「跟上個月比」
「月底預估」看起來是五個功能，各查一支的話這頁要排隊九次。

實際上它們全部是**同一份資料的不同切法**：一支 `getDailyTotals()` 撈近 75 天每日小結，
再用純函式 `derivePulse()` 換算出全部五個數字。首頁維持五支查詢。

新功能要往首頁加東西之前，先問「這能不能從已經撈回來的資料算出來」。
月結算卡片的數字就是這樣改成從 `getMonthlyTotals` 的聚合結果算的，省掉最大的那一支。

## 帳本一有真資料，測試的「假設空帳本」就會爆（2026-08-21）

匯入 3~8 月舊帳的當下，`scripts/verify.mjs` 從 87 全過變成兩項失敗，
兩項都不是程式壞了，是測試自己寫死了「帳本裡本來沒東西」：

- **各分類百分比加起來接近 100**：它拿整頁的文字去抓 `\d+%`。
  以前八月沒有上個月可比，`CompareLine` 回 null；有了七月的資料之後，
  頁面上多了一句「比上個月同一時候少 24,178（−90%）」，那個 90 也被抓進去，
  加起來變 164。修法是只掃 `data-testid="category-breakdown"` 那一塊。
- **待結清整段中斷**：測試寫死「還有 1 筆沒結清」，而匯入建了三筆真的
  （押金、租屋補助、媽媽借款）。更危險的是 `getByRole('button', { name: '標記結清' })`
  在頁面上有四顆按鈕時會中斷 —— 而如果 Playwright 選的是第一顆，
  它會去結清 Gino 真的押金。修法是先數一次當基準、斷言用基準加一，
  按鈕一律用 `page.locator('li').filter({ hasText: MARK })` 限定在測試自己那一列。

規則：**測試裡任何「數量等於 N」「頁面上只有一個 X」的斷言都要先問一句
「Gino 自己的帳會不會也算進去」**。這跟 2026-08-21 那條「不要讓測試去點
會自己挑對象的功能」是同一個病：測試假設了它獨佔這個資料庫，但它沒有。

順帶一提，同一批改動也讓 `formatSigned(0)` 印出「−0」曝光了 ——
以前沒有 0 元的非開伙紀錄，匯入「回家沒花費」那種之後才冒出來。
新資料形狀會照亮舊程式沒想過的分支，匯入完值得把每一頁都翻一遍。

## `drizzle-kit push` 在這個資料庫上會崩（2026-08-21）

要加 `transactions.settlement_id` 與 `settlements.due_month` 的時候，`npm run db:push`
在「Pulling schema from database」之後直接丟：

```
TypeError: Cannot read properties of undefined (reading 'replace')
    at .../drizzle-kit/bin.cjs:17861   // checkValue.replace(/^CHECK\s*\(\(/, ...)
```

它在解析既有資料庫的 CHECK 約束時拿到 undefined。Supabase 的資料庫裡本來就有一些
不是我們建的約束，drizzle-kit 0.31 讀不動。這不是我們的 schema 寫錯。

**做法**：欄位自己下 SQL 加，schema.ts 照樣寫（型別要對得起來），不要為了讓
`db:push` 開心而改資料模型。

```sql
alter table transactions add column if not exists settlement_id uuid;
alter table settlements  add column if not exists due_month text;
alter table transactions add constraint transactions_settlement_id_fk
  foreign key (settlement_id) references settlements(id) on delete set null;
create index if not exists transactions_settlement_idx on transactions (settlement_id);
```

`schema.ts` 那邊 `settlementId` 沒有寫 `.references()`：`settlements` 反過來也指向
`transactions`（`origin_transaction_id`），兩張表互相參照在 drizzle 的型別上會繞不出來。
約束在資料庫裡是真的存在的，只是不由 drizzle 產生。

## 提醒如果解不掉，人就會去造假資料（2026-08-21）

Gino 的原話：「押金我要等到明年退租才拿得到，那個沒結清一直放在首頁，
我會很忍不住想要把他結清消除，但又無法。」

規格書 2.2 寫「待結清項目沒結清就要一直看得到」，原本的實作是「只要 status='open'
就常駐首頁」。字面上沒錯，但對一筆一年後才會動的押金來說，那個提醒每天都在說
「你有事沒做」，而使用者**無法把它做完**。這種提醒的唯一出路是按下結清 —— 也就是
系統親手教人在自己的帳本上說謊。

修法是分開「不會消失」跟「天天擋路」：加預計時間，首頁只提醒到期／過期／沒寫時間的，
其餘在待結清頁的「還早」區。**沒寫時間的故意還是會吵** —— 連自己都說不出什麼時候
會回來的錢，才是真正會被忘記的那種。

一般化：**任何常駐提醒都要問一句「使用者現在有辦法把它解掉嗎？」**
沒辦法的話，它就不該待在最顯眼的位置，否則使用者會用假動作讓它閉嘴。

## Supabase 本來就有一張 `auth.users`（2026-08-26）

多人改造的遷移腳本先問「users 表存在嗎」再決定要不要建：

```sql
select 1 from information_schema.tables where table_name = 'users'  -- 錯
```

**永遠回答存在。** Supabase 自己的登入系統就有一張 `auth.users`，
而 `information_schema.tables` 是跨 schema 的。結果是跳過建表，
下一步查 `public.users` 就炸 `relation "users" does not exist`。

第一次預演就撞到了，所以沒有寫進資料庫，但如果那一步剛好是可以略過的、
後面才炸，就會留下改到一半的資料表。

**做法**：任何一支查 `information_schema` / `pg_class` / `pg_constraint`
來判斷「東西在不在」的程式，一律加上 schema 條件：

```sql
where table_schema = 'public' and table_name = 'users'
-- pg_class / pg_constraint 要 join pg_namespace 再比 nspname = 'public'
```

順帶一提，`gen_random_uuid()`、`auth.users` 這些是 Supabase 預設就有的東西，
不要假設這個資料庫是乾淨的空白 Postgres。上面那條
「`drizzle-kit push` 在這個資料庫上會崩」也是同一個根源：
資料庫裡有一堆不是我們建的東西。

## 加「一定要有值」的欄位到已經有資料的表，順序不能反（2026-08-26）

四張表都要加 `user_id not null`，但表裡已經有 397 筆帳。
直接 `add column user_id uuid not null` 會被資料庫擋下來（現有的列沒有值可以填）。

必須拆成三步，而且中間不能失敗：

```sql
alter table transactions add column if not exists user_id uuid;   -- 1 先允許留空
update transactions set user_id = $1 where user_id is null;        -- 2 補上主人
alter table transactions alter column user_id set not null;        -- 3 才鎖起來
```

`drizzle-kit push` 對這種情況只會叫你自己想辦法，所以這段寫成
`src/db/migrate-multiuser.ts`，每一步都先檢查「是不是已經做過了」，可以重複跑。

**這也是為什麼那支腳本預設是預演。** 它動的是 Gino 真的帳本，
先印出「會把 397 筆歸給誰」讓人看過，再加 `--write`。

## 多人系統裡，「漏寫一個 where」不會有錯誤訊息（2026-08-26）

改成多人的時候，最省事的做法是讓查詢自己去讀 cookie 算出「現在是誰」，
呼叫端一行都不用改。**沒有採用**，因為那樣漏掉一支查詢時：

- 不會編譯失敗
- 不會丟錯誤
- 只會安靜地把別人的帳顯示給錯的人看

改成「`userId` 是每一支查詢必填的第一個參數」之後，少傳一支 TypeScript 就編不過。
改動大得多（30 幾個檔案），但**漏不掉**。cron 與 LINE webhook 沒有 cookie 可讀，
這個做法它們也剛好用得上。

同理，寫入端的 `update` / `delete` 就算前面已經讀出來確認過歸屬，
`where` 還是要再帶一次 `user_id` —— 只檢查一次等於相信「兩次查詢之間沒有人動手腳」，
而這裡猜錯的代價是別人可以改你的帳。

## 測試卡住不動時，先看 3000 埠上跑的是哪一版（2026-08-26）

多人改造完，`npx playwright test` 跑了十分鐘一個字都沒印出來。
不是測試慢，是 `playwright.config.ts` 裡的 `reuseExistingServer: true` ——
它看到 3000 埠有人在聽就直接用，而那個伺服器是**五天前**啟動的
`npm run start`，跑的是舊版程式。

舊版的登入頁只有「密碼」欄位，測試在等一個不存在的「名字」欄位，
就這樣安靜地等到逾時。畫面上什麼錯誤都沒有。

`reuseExistingServer` 本身是對的（不必每次重開省很多時間），
但它預設**不會**檢查那個伺服器是不是你這次要測的版本。

**做法**：改完程式跑測試之前，先確認一下：

```bash
curl -s http://localhost:3000/login | grep -o 'placeholder="[^"]*"'
```

看到的欄位跟你剛改的對不起來，就把它關掉重開：

```bash
# 找出佔用 3000 埠的行程（PowerShell）
Get-NetTCPConnection -LocalPort 3000 -State Listen | Select OwningProcess
Stop-Process -Id <那個 PID> -Force
npm run build && npm run start
```

同一個道理：**改完程式一定要 `npm run build` 再 `npm run start`**。
`npm run start` 跑的是 `.next/` 裡上一次 build 的產物，不會自己重新編譯。

## 兩套驗收只有一套在維護，另一套壞了半個月沒人知道（2026-08-26）

這個專案有兩套驗收：`scripts/verify.mjs`（93 項）與 `tests/ledger.spec.ts`（Playwright）。
平常跑的是前者，所以介面一改，被修的也只有前者。

2026-08-26 做多人改造時第一次認真跑 Playwright 那套，13 條裡有 5 條是壞的，
而且**每一條都不是那天改壞的**：

| 壞掉的原因 | 什麼時候壞的 |
|---|---|
| `record()` 沒有先按「自己填」展開手動表單 | 2026-08-20 首頁改成預設收合 |
| 月結算的期望值寫死成空帳本的數字 | 2026-08-21 匯入 397 筆舊帳 |
| 找「還有 N 筆沒結清」，但畫面上的文案是「有 N 筆該追了」 | 首頁提醒改版時 |
| `getByRole('button', {name:'標記結清'})` 抓到一整把 | 帳本裡開始有多筆待結清時 |
| `toHaveURL(/\/transactions/)` 在 `/transactions/<id>` 上就成立 | 一直都是，只是以前跑得夠快沒撞到 |

最後一條特別值得記：那條斷言本來是要等「存檔完成、跳回明細頁」，
但因為少了結尾的 `$`，它在還停在編輯頁時就通過了 ——
測試接著去查資料庫，讀到的還是舊金額，畫面上按鈕還寫著「儲存中…」。
**URL 斷言一律要把範圍夾死**（`/\/transactions$/`），不然它遲早會變成一個
「看起來有等、其實沒等」的假等待。

教訓不是「要記得同步兩套」，是**同一件事不要有兩套會各自腐爛的實作**。
在合併成一套之前，至少改介面時兩邊都要跑一次。
